## Problem Statement
The existing "Using AI at Home and School" standard (`standard/using-ai-at-home-and-school.md`) is a printable document only — it has no enforcement mechanism. Schools and families have no way to actually run these rules against a real AI tool; adoption depends entirely on humans reading and remembering a poster. The goal of this session was to turn the standard into working software: an open-source guardrail library that any AI application can wrap around a model, so the age-band rules and required explanations in the standard become code, not just policy on paper — while explicitly avoiding a pure "block and say nothing" pattern in favor of the standard's educational-refusal principle.

## What Makes This Cool
Nothing in the current AI-safety-tooling landscape does age-banded policy + mandatory plain-language explanation the way this standard defines it. Existing guardrail SDKs (Llama Guard, NeMo Guardrails, Guardrails AI, ShieldGemma, Granite Guardian) are all classifiers — "is this harmful: yes/no." None of them encode "explain WHY, tied to real-world consequence, and change the specific policy by a child's age band." The "whoa" moment named this session: a principal or counselor watching the tool refuse a live self-harm or PII-leak prompt and explain itself in age-appropriate language, in real time.

## Constraints
- Goal is open-source/research contribution, not revenue or fundraising.
- First external touchpoint is school reviewers, most of whom are non-technical (principals, counselors, teachers) — the artifact needs to be legible to a non-engineer.
- The standard document (`standard/using-ai-at-home-and-school.md`) is the canonical source of truth for policy language. The runtime explanation templates are **parsed from** that markdown — the markdown is never generated from a separate schema, and the software must not fork or hand-duplicate the language.
- Distribution: the library itself ships fully open-source; the demo/pilot site is closed and token-gated, restricted to invited school reviewers.
- This domain is safety-sensitive (self-harm, PII, sexual content categories) — no pilot invite goes out without an explicit human safety/legal review sign-off (see Next Steps).

## Premises
1. Wrap an existing open-weight classifier (Llama Guard 3 1B via Ollama) rather than train a new self-harm/PII detector from scratch — classification is a commoditized, solved problem in 2026.
2. The differentiated IP is the age-band policy engine + the standard's explanation templates, not detection accuracy.
3. Build the token-gated website chat demo and the library in parallel (see Recommended Approach) rather than sequencing one before the other; once the demo works live, record a screen-walkthrough too, so both artifacts exist.
4. Distribution: the guardrail library ships open-source (GitHub + PyPI for v1 — see Open Questions on a future JS/npm port); the demo site stays closed/token-gated for school pilots only.

## Policy Categories (from the standard's universal strip + allowed-row behavior)
The classifier layer's output must map onto these categories, each carrying its own age-band × action × explanation-template lookup:
1. AI self-identification failure (tool implying it's a person/friend/counselor)
2. Self-harm / suicide / disordered-eating content or roleplay
3. Sexual content involving a minor, or romantic/sexual roleplay
4. Sexual/nude imagery of a real person, including deepfake/"nudify" requests
5. Helping a child hide activity from a parent, meet a stranger, or share identity/location/contact details
6. Soliciting or collecting a child's PII (name, address, school, phone, photos)
7. Learning-integrity shortcut (child asking the tool to just hand over the answer/write the work for them) — not a safety refusal, but the standard's required "explain the long-term cost" behavior
8. Out-of-policy tool warning (child references or asks about an unfiltered/uncensored/no-guardrail tool)

**Detection is two layers, not one classifier.** Llama Guard 3 1B natively covers categories 2, 3, 4, and 6 (self-harm, sexual content, sexual imagery, PII exposure — its trained safety taxonomy). Categories 1, 5, 7, and 8 are policy/behavioral patterns, not safety-classifier categories, and Llama Guard does not detect them. v1 adds a lightweight supplementary detector for these four — a prompt-based intent classifier (a single cheap LLM call asking "does this message match pattern X/Y/Z," reusing the same local Ollama model already running for the benign-path chat) rather than keyword/regex matching, which is brittle for natural language. This supplementary layer is still "one classifier backend" from the library's perspective (Llama Guard remains the only *safety* backend behind the pluggable interface); the prompt-based layer is policy logic, not a second safety backend, and is not subject to the backend-swappability interface.

**Multi-category conflicts:** when a message matches more than one category, apply this fixed priority order (highest wins): 2 (crisis) > 3 (sexual content, minor) > 4 (deepfake/nudify) > 6 (PII) > 5 (hide-from-parent/stranger) > 8 (tool warning) > 1 (self-id) > 7 (learning-integrity). Only the highest-priority category's action and explanation fire; lower-priority matches are logged but not surfaced to the user in the same turn.

**Scope limitation (explicit, not silent):** v1 classifies each message independently. Multi-turn/session-level patterns — incremental PII disclosure across several turns, grooming-adjacent conversational patterns that only emerge over a conversation — are a known, real limitation and are explicitly out of scope for v1. This is a scoped limitation, not an oversight; revisit once the single-turn version is validated with a real pilot.

## Policy Schema
`policy.yaml` maps `(age_band, category) → (action, explanation_template_ref)`.
- **age_band:** one of `8-11`, `12-15`, `16-18` — selected via an explicit dropdown at the start of a demo session (self-declared for v1; not age-verified — see Open Questions for a future token-embedded age band).
- **action:** one of `allow`, `allow_with_explanation` (learning-integrity case), `refuse_with_explanation`, `refuse_and_route_to_crisis_resource` (category 2 only, every age band, regardless of policy.yaml override).
- **explanation_template_ref:** a key into the template library generated by the markdown parser (see Next Steps #4), never hand-written prose duplicating the standard.

**`allow_with_explanation` decision rule (category 7 only):** enforced as a system-prompt constraint on the benign-path model itself, not a separate output filter — e.g. "explain the reasoning/method behind the answer; never output the complete final answer, essay, or solution the user could submit as their own work directly." This is a prompt-engineering rule on the one benign-path model, applied per age band using the standard's own age-banded language (8-11: show the steps; 12-15: think it through together; 16-18: draft-then-edit their own work).

**Worked example (`policy.yaml` excerpt, all 8 categories, one age band shown — 12-15):**
```yaml
12-15:
  1_self_identification_failure: {action: refuse_with_explanation, template: universal.ai_identity}
  2_self_harm: {action: refuse_and_route_to_crisis_resource, template: universal.crisis_route}
  3_sexual_content_minor: {action: refuse_with_explanation, template: universal.no_sexual_content}
  4_deepfake_nudify: {action: refuse_with_explanation, template: universal.no_deepfake}
  5_hide_from_parent: {action: refuse_with_explanation, template: universal.no_secret_contact}
  6_pii_solicitation: {action: refuse_with_explanation, template: universal.no_pii}
  7_learning_integrity: {action: allow_with_explanation, template: band_12_15.learning_integrity}
  8_unfiltered_tool_warning: {action: allow_with_explanation, template: band_12_15.no_safety_filter_warning}
```
Category 8's action is `allow_with_explanation`, not a refusal: the tool doesn't block the child from mentioning an unfiltered tool, it responds with the standard's warning language (e.g., 12-15: "some AI tools have no safety filters at all — downloadable models, uncensored apps") and continues the conversation. The full table (8 categories × 3 age bands) is built in Next Steps #3, generated from the parser output, not hand-written in full here.

## Safety Fallbacks (non-negotiable, not configurable per age-band)
- **Real self-harm disclosure vs. a test prompt:** the demo cannot reliably tell the difference. Every `refuse_and_route_to_crisis_resource` response — real or test — always names a real crisis line and a "talk to a trusted adult" line, verbatim from the standard's universal strip. The demo UI carries a permanent visible banner: "This is a safety-engine demo, not a real support service. If you or someone you know is in crisis, contact [crisis line]."
- **Classifier unavailable/erroring (Ollama down, timeout, malformed output):** fail closed. Default action is `refuse_with_explanation` using a generic "the safety check is temporarily unavailable, try again shortly" template — never fail open to an unfiltered response.
- **Transcript logging:** demo transcripts are logged for debugging only, with any user-typed PII redacted before storage, retained a maximum of 30 days, and never used to train or fine-tune any model.

## Approaches Considered
### Approach A: Minimal viable demo only
FastAPI service wrapping Llama Guard 3 1B via Ollama (free, local, no GPU), `policy.yaml` keyed by age-band × category, explanation text parsed from the standard doc, single-page htmx chat, shared-secret token gate. Effort: S. Risk: Low. Ships fastest; zero API cost. Rejected as the sole path — the user wants the library, not a throwaway script, from day one.

### Approach B: Full pluggable multi-backend library first
A typed library with swappable classifier backends (Llama Guard, OpenAI moderation, ShieldGemma) built out immediately, ahead of any named user. Effort: XL. Risk: Medium-High — this is premature abstraction with zero second backend actually needed yet. Rejected as originally scoped; folded into the Recommended Approach at reduced scope (see below).

### Approach C: Incident-replay audit tool
Skip the live chatbot; annotate a synthetic incident transcript turn-by-turn showing where the guardrail would have intervened. Stronger board-room artifact, no hosting/token support burden — but loses the "watch it happen live" moment that most excited the user this session. Not selected.

## Recommended Approach
Build a **real, importable library** (not a throwaway script) — but scope it to **one safety-classifier backend (Llama Guard 3 1B via Ollama) plus one lightweight prompt-based policy-category detector, behind a documented, minimal interface**, not three safety backends implemented in parallel. The interface is written so a second safety backend *can* be added later without a rewrite, but no second backend is built until a real need for one shows up — the same deferral discipline already applied to CI/CD and token expiry. The library ships as a Python package (PyPI) for v1. The token-gated demo website is a consumer of this library's public API, built as two genuinely parallel tracks in the same repo: the demo UI/chat shell is built immediately against a mocked version of the library's interface, while the real library (classifier + policy engine + parser) is built on its own track; the two tracks converge when the demo swaps the mock for the real library. This is not a duplicate implementation — the mock and the real interface share one contract from day one. This keeps the user's core requirement — a real library, not a demo script — while cutting the part of the original "build the full pluggable library now" ask that had no user behind it yet.

## Success Criteria
- A named school principal or counselor has used the live token-gated demo themselves (not just watched a screen share) and reacted to at least one real-time refusal + explanation.
- Classification + explanation response lands in under 2 seconds to first token in the live demo (echoes the Next Steps #6 target so it's tracked, not silently dropped).
- The guardrail library has a public repo with one documented safety-classifier-backend interface plus the policy-category detector, passes its own test suite against the standard's parsed explanation templates (no hand-duplicated policy text) and against the worked policy.yaml example, and fails closed (never open) when the classifier is unavailable.
- The safety-fallback behavior (crisis routing, closed-failure default, transcript redaction/retention) has been reviewed and signed off before any pilot invite is sent.
- A screen-recorded walkthrough exists as a secondary artifact once the live demo works.

## Reviewer Concerns
Three rounds of adversarial review (5/10 → 7/10 → 8/10) fixed 26 issues. These three remain unresolved after the 3-round cap — none blocks starting the work, but each should be resolved before or during Track 1 implementation:

1. **[Consistency]** Category 7's description ("explain the long-term cost," in Policy Categories) and its decision rule ("teach method, withhold final answer," in Policy Schema) aren't clearly the same behavior — the decision rule never requires stating *why* the shortcut costs the child long-term, only that it withholds the answer. Fix: add a line requiring the age-appropriate "why this matters" text to accompany the withheld-answer behavior.
2. **[Consistency/Clarity]** Ambiguous whether the supplementary prompt-based detector (categories 1/5/7/8) shares the same "documented, minimal interface" as the Llama Guard backend, or has its own separate, non-swappable interface — the doc implies both at different points. Fix: one clarifying sentence in Track 1 step 2.
3. **[Feasibility]** The under-2-seconds-to-first-token target doesn't account for the latency of the two-layer detection pipeline (Llama Guard call + supplementary detector call, potentially plus the benign-path model call). Fix: decide during Track 1 step 2 whether these run concurrently or the supplementary check is skipped once Llama Guard already flags a message, and validate the target holds before it's treated as met.
